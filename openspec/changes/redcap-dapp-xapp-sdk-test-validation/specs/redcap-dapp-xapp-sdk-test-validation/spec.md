## ADDED Requirements

### Requirement: Staged dApp/xApp SDK Validation Gates
The project SHALL define staged validation gates for RedCap dApp/xApp SDK testing: SDK unit checks, SWIG checks, E3 loopback checks, small RFsim marker validation, and 56 UE / 5 MHz BWP stress validation.

#### Scenario: Gate list is discoverable
- **WHEN** the validation project documentation is inspected
- **THEN** it lists Gate A through Gate E with purpose, acceptance evidence, and limitation notes

#### Scenario: 56 UE stress is not used as static proof
- **WHEN** only static checks have passed
- **THEN** the project does not claim 56 UE / 5 MHz BWP runtime PASS

### Requirement: dev_refer-First Reference Coverage
The validation workflow SHALL use local `dev_refer/` content as the primary reference for dApp/xApp SDK tests.

#### Scenario: Required dApp references exist
- **WHEN** the static validation checker runs
- **THEN** it verifies `dev_refer/dapp_dev_need/libe3/`, `dev_refer/dapp_dev_need/dApp-library/`, and `dev_refer/dapp_dev_need/dApp-openairinterface5g/`

#### Scenario: Required xApp references exist
- **WHEN** the static validation checker runs
- **THEN** it verifies `dev_refer/xapp_dev_need/` and `openair2/E2AP/flexric/`

### Requirement: dApp Test Contract
The dApp SDK test contract SHALL model I/Q observation input, UE priority hints, PUCCH/PUSCH PRB ratio intent, and apply/reject decisions.

#### Scenario: dApp contract rejects invalid inputs
- **WHEN** a dApp allocation request has missing I/Q metadata, invalid RNTI, invalid 5 MHz BWP profile marker, or PUCCH/PUSCH ratios outside the accepted range
- **THEN** the SDK test helper returns a reject decision with a reason string

#### Scenario: dApp contract accepts a bounded allocation
- **WHEN** a dApp allocation request has valid RNTI, a 5 MHz BWP profile marker, bounded PUCCH/PUSCH ratios, and a non-negative UE priority
- **THEN** the SDK test helper returns an apply decision and exposes expected marker fields

### Requirement: xApp Priority Hint Contract
The xApp SDK test contract SHALL compute UE priority hints and deliver them to the dApp-facing contract instead of directly scheduling PUCCH/PUSCH.

#### Scenario: xApp ranks UE priorities
- **WHEN** the xApp test helper receives UE metrics with distinct weights
- **THEN** it returns a deterministic priority order and identifies the top UE

#### Scenario: xApp output is consumable by dApp
- **WHEN** a priority hint generated by the xApp test helper is passed to the dApp test helper
- **THEN** the dApp helper uses the priority value in its allocation decision metadata

### Requirement: SWIG Evidence Boundary
The validation workflow SHALL distinguish pure Python SDK helpers from SWIG-backed Python-to-C/C++ bindings.

#### Scenario: SWIG definitions are present
- **WHEN** the static validation checker runs
- **THEN** it verifies local SWIG interface files for `libe3` and I/Q saver references

#### Scenario: Python binding is not overclaimed
- **WHEN** generated SWIG modules are not present or cannot be imported
- **THEN** the checker reports the status as missing or fallback and does not treat pure Python helper execution as SWIG PASS

### Requirement: Bilingual SDK Documentation
The validation project SHALL provide paired English and Traditional Chinese documentation for SDK APIs, commands, examples, visualization, markers, and known gaps.

#### Scenario: Bilingual docs are paired
- **WHEN** the documentation checker runs
- **THEN** both `README.en.md` and `README.zh-TW.md` exist for the project docs

#### Scenario: API and command content is separated
- **WHEN** either documentation page is inspected
- **THEN** it contains separate API/config, command usage, step-by-step recap, expected markers, and limitations sections

### Requirement: Workflow v3 Follow-up Recording
The validation workflow SHALL record missing or failed SDK test coverage as follow-up work for `redcap_oran_sdk_workflow_v3` without reopening completed tasks.

#### Scenario: Follow-up ledger exists
- **WHEN** the validation project is inspected
- **THEN** it contains a follow-up file that can record failed gates, missing runtime hooks, and next pull items
